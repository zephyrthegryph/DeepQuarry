# Review of native-v2, 7 October 2026

Scope: `codex/native-v2` from `ac1af55d1a` to `0abecd06c0` (120 commits), with `STATUS.md`,
`PHASE2_PROGRESS.md`, `phase0/`, the contract documents and the probe receipts under
`E:/dmb-native-v2-phase0/`. No code was run for this review.

`DESIGN.md` revision 5 makes the plan below binding. Where this review and revision 4 disagree,
revision 5 wins.

## Verdict

Phase 1 produced a real compiler: a full, deterministic, published DMB/RSC pair in 33 s. Phase 2
then went wrong in the way the old branch did. Incremental builds are slower than building from
scratch, and banned patterns are back.

The root cause is not a caching bug. The design assumed the stages that rerun on every build
would cost about 1 s in total. They actually cost about 55 s. Caching cannot remove that cost;
only stage throughput work can. So the plan changes:

- Stop extending the disk cache.
- Return to Phase 1 and make every stage fast, guided by a profiler and judged by CPU time.
- Build the daemon next, so the whole-program state stays in memory between builds.
- Only then return to no-daemon disk caching.

## What is working (keep it)

- **Full cold compile and publication.** Probe 40 compiled all 43,919 types and 64,964 bodies
  in 33.1 s with test defines and 35.0 s with server defines, at 2 workers. This is down from
  104–131 s at `ac1af55d1a`.
- **Determinism.** DMB, RSC and pair-marker hashes match across worker counts.
- **Incremental correctness where measured.** In cohorts C, F, G, I, J and K, the edited build's
  DMB and RSC were byte-identical to a fresh build of the same inputs.
- **Structure.** The crate layout follows §3.8 (`dm-tree`, `dm-link`, `dm-cache`, `dm-wire`,
  `dmbc`). The old store, work and daemon crates are gone, and the Rust total fell from about
  150,000 lines to 85,196.
- **Contracts.** `PREPROCESS.md`, `LINK.md` and `PUBLISH.md` exist with fixtures. Canonical
  paths were corrected against DreamMaker.
- **Plumbing.** The snapshot-fed `--verify` oracle, session records, the worktree build lock,
  pair authentication, `stats` and `explain` exist, and the tiny-project contract checks pass.
- **Unchanged builds** went from 12.7 s to 3.4 s.

## Findings

### F1. Incremental builds are slower than cold builds (critical)

| Cohort | Populate | Unchanged | Body edit | Cold |
| --- | ---: | ---: | ---: | ---: |
| G | 79.2 s | 3.4 s | 64.1 s | 77.2 s |
| I | 109.4 s | 3.6 s | 71.9 s | 56.2 s |
| J | 142.7 s | 4.4 s | 110.3 s | 82.9 s |
| K | 196.7 s | 3.9 s | 84.1 s | 72.6 s |

The body-edit target is 1.5 s without a daemon. Cold builds regressed from Phase 1's 33 s to
56–83 s once the Phase 2 code paths were added.

### F2. The stages that rerun every build are 10–50× over the design's hypotheses (critical, root cause)

These are body-edit stage times from cohort F, where 77,563 procedures were reused and one was
recompiled:

| Stage | Measured | DESIGN.md r4 hypothesis |
| --- | ---: | ---: |
| Frontend (directives, expansion, parse) | 13.5 s | ~15 ms |
| Resources and maps | 6.9 s | ~5 ms |
| ABI preparation | 4.8 s | (not modeled) |
| Initializers | 4.2 s | (memoized) |
| Lowering, one miss | 13.2 s | ~5 ms |
| Link | 8.1 s | ~200 ms |
| Composition | 2.8 s | (part of encode) |
| Publication | 4.4 s | ~200 ms |

In cohort K the frontend took 21.9 s and lowering 14.9 s for a single miss. These stages are
meant to be cheap whole-program passes. No amount of caching makes a 13 s frontend or an 8 s link
fit a 1 s edit. This is Phase 1 throughput work, and the design's §6 numbers were wrong. That is
the reviewer's error as much as the implementation's.

### F3. Cache hits cost more than recomputing (high)

Phase 1 lowered all 64,964 bodies cold in 6.3 s (probe 32). Reusing 77,563 cached procedure
records then took 3.4–43.8 s across cohorts G to K. The hit path decodes, copies and rebuilds
records ("retaining decoded candidates instead of repeated deserialization"). That fails the
design's rule that a memo must pay back 10× its validation cost. Hits must be read in place
(zero-copy), or that memo is not worth having.

### F4. Banned patterns have returned (high)

- **A byte limit that skips work.** Cohort I: "Tree exact key 112800639 bytes exceeds 32MiB;
  key_oversize1/skipped_budget1". A limit changed what the build did. The limit rule (§2.5)
  allows a limit only to evict or queue.
- **The object tree on disk.** A 112.8 MB key and a 23.9–122 MB payload are written and read per
  build. §6.4 deferred any tree persistence until a profile asked for it, and the tree should be
  keyed by a hash of the ordered skeleton sequence, not a 112 MB key.
- **"Bounded admission" machinery.** Pending budgets, admission, receipts, certification and
  leases in cache code are the vocabulary and the failure mode of the old branch: population lost
  31,272 records to budget and storage errors in cohort E.
- **Memory.** Peak private memory is 3.0–3.5 GB per build at 2 workers, against a 0.45–0.6 GB
  estimate. Nothing has measured where it goes.

### F5. Phase discipline slipped (high)

Phase 0 is still open: ten sampled frames and parity evidence are outstanding. Phase 1 has not
met its 30 s target or its parity gate. Phase 2 is nonetheless the main work stream. DESIGN.md
allows one phase open at a time.

### F6. No profiler; noisy measurements (high)

- **Sampling stopped.** samply raised administrator prompts and was stopped at the user's
  request. Since then only stage timers exist, and they cannot explain, for example, why one miss
  costs 13–15 s of lowering. This is the old branch's whack-a-mole pattern.
- **Contended runs.** Most runs had 7–21 competing Cargo/rustc processes, plus the game and
  DreamDaemon. Population time ranged from 79 s to 197 s, so changes between cohorts cannot be
  attributed.
- **Two workers.** Every benchmark used 2 workers on an 8-core, 16-thread machine. The design's
  targets assume the machine's cores.

### F7. Documentation and code shape (medium)

- **A dated log.** `PHASE2_PROGRESS.md` is a dated cohort log (A–K) in compressed prose. The
  rules call for `STATUS.md` updated in place and numbers in `results.jsonl`.
- **An oversized file.** `dm-codegen-byond/src/simple.rs` is 12,028 lines against a 1,000-line
  cap, and 66 lines exceed 200 characters.
- **Missing test evidence.** No full `cargo test` run is recorded. Only focused checks are cited.
- **Disk space.** The default cache on C: filled the drive (StorageFull, OS error 112).

## Revised plan (binding through DESIGN.md r5)

The phases are renumbered from here. The old Phase 2 (disk cache) and Phase 3 (daemon) swap
places, and Phase 1 is reopened as stage throughput work.

### Step 0: Freeze and clean up (≤ 1 day)

1. Freeze disk-cache work. Code from cohorts A–K stays and must keep compiling, but receives no
   new features until the new Phase 3. Bug fixes needed by the oracle are allowed.
2. Remove the tree disk admission (the tree key/payload path) and every byte limit that causes a
   skip, as opposed to an eviction. With `--no-cache` and with the cache, output must be
   unchanged.
3. Fold `PHASE2_PROGRESS.md` into `STATUS.md` (current state only). Move per-cohort numbers into
   `results.jsonl`, and move the narrative to `archive/`.
4. Run the full `cargo test --workspace` once in release mode and record the counts in
   `STATUS.md`. Fix or list every failure.

Exit: the frozen state compiles, tests are recorded, and the tree-on-disk and skip-on-limit paths
are gone.

### Step 1: A profiler that needs no administrator rights (≤ 1 day)

1. Instrument every stage and its main sub-stages with `tracing` spans, plus per-thread CPU time.
   Write a Chrome trace (`tracing-chrome`) with `--trace <file>`, viewable in Perfetto. Also write
   a folded-stack flamegraph from the same spans (`tracing-flame` and `inferno`).
2. Count allocations per stage (a counting global allocator behind a feature flag) and record
   peak memory per stage.
3. This is the profiler. samply and other tools that need elevation are not used (user decision,
   7 October).

Exit: one cold trace and one body-edit trace of the full project, with per-stage wall time, CPU
time, allocations and memory, and the ten heaviest spans written up in `STATUS.md`. This replaces
the deferred Phase 0 "ten sampled frames" gate.

### Step 2: Benchmark protocol (half a day, alongside Step 1)

1. Acceptance is judged by CPU time, not wall time (user decision, 7 October), because the
   machine is shared. `dmb-bench` reports per stage: critical-path CPU (the slowest thread's CPU
   time in each stage, summed along the pipeline), total CPU, and bytes read and written. The
   definitions are in DESIGN.md §6.5. Competing processes are recorded, never stopped.
2. Acceptance runs use 8 workers (the physical core count) and take the median of three. Runs at
   2 workers continue as a regression series.
3. Every row reports critical-path CPU, total CPU, I/O bytes, wall time (for information only),
   peak private memory and the competing-process count. On Windows, per-span CPU uses
   `QueryThreadCycleTime`, because `GetThreadTimes` only advances in 15.6 ms ticks.
4. The shared cache moves to `E:\.dmbd\cache\` by default (user decision, 7 October).
   `DMB_CACHE_DIR` still overrides it, and free space is checked before population.

Exit: a CPU-time baseline of the current cold build at 8 workers (critical path, total CPU,
I/O), median of three runs, in `results.jsonl`.

### New Phase 1: Stage throughput (≈ 4–7 days)

Work strictly from the Step 1 traces, one stage at a time, worst first. Each change cites its
trace before and after.

Per-stage cold budgets, at 8 workers, in critical-path CPU. DESIGN.md §6.0 adds total-CPU and
I/O budgets beside these:

| Stage | Budget | Latest measured (2 workers, contended) |
| --- | ---: | ---: |
| Input scan and hashing | ≤ 0.5 s | — |
| Frontend: directives, expansion, parse | ≤ 3 s | 7.4–21.9 s |
| Semantic tree and occurrence table | ≤ 1 s | — |
| Resources and maps (cold hashing) | ≤ 2 s | 4.7–15.3 s |
| ABI preparation and initializers | ≤ 1.5 s | 5–9 s |
| Lowering, all bodies | ≤ 3 s | 6.3 s |
| Link | ≤ 1 s | 4.7–9.2 s |
| Composition, encode, publication | ≤ 1.5 s | 7–19 s |
| **Total cold** | **≤ 15 s** | **33 s (Phase 1), 56–83 s (Phase 2)** |
| **Peak private memory** | **≤ 1.5 GB** | **3.0–3.5 GB** |

The same work restores the Phase 1 parity gates:

- order fixtures match DreamMaker;
- no new divergence against the frozen baseline;
- `cargo test` green.

Split `simple.rs` along the boundaries the traces expose while working in it.

Exit:
- every stage within budget;
- cold build ≤ 15 s (≤ 20 s acceptable if one stage has a written, trace-backed reason);
- memory ≤ 1.5 GB;
- parity gates as above.

If a stage misses its budget after two trace-guided rounds, stop and report the trace to the
human (the stop-loss rule).

### New Phase 2: Daemon with in-memory sessions (≈ 3–5 days)

The daemon keeps everything the whole-program stages need resident between builds: expanded
regions and fragments, the semantic tree, the occurrence table, lowered symbolic code and the
previous linked image. A body edit then costs:

- re-expanding one region;
- lowering one body;
- relinking and encoding;
- publishing.

The disk cache is not on the hot path in this phase. The daemon may read the existing cache only
to warm a new session, and a fresh session may simply cold-build. The work items:

- `dmbd` and `dmbc`;
- the session lock, shared with no-daemon runs;
- the draining version handshake;
- cancellation before publication;
- idle trimming;
- the in-memory Δ filter for regions.

Exit:
- body edit ≤ 1 s, new var or proc ≤ 2.5 s and unchanged ≤ 100 ms, end to end;
- the oracle (DMB, RSC, diagnostics) clean on the edit corpus and a 300-commit replay;
- six worktrees within targets;
- daemon private memory ≤ 1.5 GB working and ≤ 0.25 GB idle.

### New Phase 3: Disk cache and no-daemon mode (≈ 4–6 days)

Resume the frozen cache code under these rules:

1. **Zero-copy hits.** Hits are read in place from mapped segments, and validation covers only
   the records used.
2. **Measured payoff.** Each memo kind must show, in a trace, a hit-path cost at most one tenth of
   recomputing the same items cold. A memo kind that fails is disabled, not tuned with budgets.
3. **No tree on disk,** unless the Phase 1 tree budget is missed and a trace shows tree rebuild
   dominating no-daemon builds. Even then, its key is the ordered skeleton hash.
4. **No admission budgets.** Population writes every computed record. Space problems are solved
   by compaction and an explicit cache drive, never by skipping records.

Exit:
- no-daemon unchanged ≤ 250 ms, body edit ≤ 1.5 s and new var or proc ≤ 2 s, end to end;
- populating the cache costs at most 20% more than a cold build;
- cache, pair and session contract tests pass.

### Phases 4–6

Phase 4 is build integration, Phase 5 is hardening and Phase 6 is lint and generator hosting.
They are unchanged from DESIGN.md r4.

## What not to do

- Don't tune caches, budgets or admission to fix a stage that is slow when cold.
- Don't benchmark acceptance numbers while other builds run.
- Don't add a new memo, store, lease, receipt or certificate concept without a design change.
- Don't keep a phase open while working on the next one.

## Decisions from the human (7 October)

1. **Profiling:** `tracing`-based profiling with no elevation is enough. samply is not used.
2. **Measurement:** acceptance uses CPU time. There will be no quiet benchmark windows. DESIGN.md
   §6.5 defines critical-path CPU, total CPU and I/O budgets accordingly.
3. **Cache drive:** the shared cache defaults to E: (`E:\.dmbd\cache\`).
