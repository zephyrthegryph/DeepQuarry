# Refresh queue diagnostic (unhooked)

This probe observes the queue before ordinary selected tests by priority. It
does not drain or flush it and does not certify a passing runtime baseline.
Queue/map scans are explicitly bounded; incomplete scans remain incomplete.
Histograms count queue entries, while `distinct` counts datum identities.

The public build entry point currently cannot compile a caller-supplied derived
DME. Do not modify the permanent manifest or add this diagnostic to game sources.
The owned paired runner creates a UUID derived DME in the actual checkout root containing an absolute
include of the current checkout's `deepquarry.dme`, followed by an absolute
include of this probe, with the existing test definitions and map configuration.
BYOND resolves resource literals from the outer DME directory, so an E-cache
manifest is insufficient even with absolute includes. The exact owned manifest
and matching outputs are preserved in the receipt directory, then removed only
after the owned job is reaped. The permanent manifest is never changed.

Before either child, authenticate the same captured non-output source roster,
ordered defines, template, compiler executable and runtime/DLL inputs. Hash the
derived DME and probe and retain their exact bytes. Revalidate that same roster
after both compiles/runtimes; positive reads alone do not certify closure.

Compile once per backend under the existing owned guardian (300 seconds), with
no native fallback. Acquire the native immutable generation and run its private
writable copies. Stage the current authenticated DLL and keep the original
checkout working directory (`-cd`). The BYOND copy must use the same current
DLL, security, map, seed, selected test order and runtime parameters.

Select `/datum/unit_test/dq_refresh_queue_diagnostic` before the same
eight focused paths used in the paired baseline. Run one world per backend,
bounded to 300 seconds, and always reap the owned tree. Preserve the JSON from
each owned runtime directory, compiler/acquisition receipts, full selected
result rows and logs. Record actual test order rather than assuming priority
establishes it. Do not substitute a standalone empty world for the game boot.

Compare queue type/mask/location histograms and unique/stale counts together
with drained count, world time and map population. A queue size difference
alone cannot distinguish initialization population from scheduling progress.
Absolute object references are process-local and must not be compared across
worlds.

The initial BYOND captures completed with the two previously observed focused
test failures and no runtimes. Their queue backlogs differed substantially,
so backlog size alone is not a compiler correctness gate. The native attempt
stopped at skin-path containment before runtime; equivalent ordinary and
extended Windows drive prefixes must be normalized before retrying. Preserve
those failed receipts and reuse the authenticated reference only with the exact
same outer manifest path and bytes. Current evidence lives under
`E:/dq-cache/dmb-native-v2/refresh-queue-diagnostic-20261010/`; no full runtime
baseline has been admitted.

Prior-reference admission compares the actually consumed DreamMaker,
DreamDaemon and DLL pins. The old native compiler and engine template were
