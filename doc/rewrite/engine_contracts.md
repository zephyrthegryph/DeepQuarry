# Engine contracts (E0)

What step E0 of the rewrite (`final_api.html` section 19) delivers, so that E1 to E6 each have their inputs and outputs named.
Nothing here has runtime behaviour except the test driver's own bookkeeping. Engines do not start in E0.

## File map

| Path | What |
|---|---|
| `code/__defines/engine/markers.dm` | Declaration markers (`CAPABILITIES`, `ACTION`, `STAT`, `SCHEMA`, `SYSTEM_ACCESSOR`, `STAGE_DEF`, `STATE_GRAPH`, `RESOURCE_DEF`, `SOURCE_DEF`, `CAPABILITY_DEF/TYPE`, `cap_keys`, and `section(name, "doc")` inside a `CAPABILITIES` block). Each expands to nothing: a declaration in the final syntax compiles and is skipped until the generator reads it. |

| `code/contracts/accessors/` | `SYSTEM_ACCESSOR` declarations (names only). |

The contracts and defines are included right after `code\__defines`, before `_helpers` (compile order 2). Engine stubs are included before
`code\_generated`. `code\tests\_tests.dm` is included just before `_unit_tests.dm` and is guarded by `UNIT_TESTS`.

## The driver

Real from E0 (pure bookkeeping): `test_rng`/`test_rolls`/`test_roll`, `test_budget`, `test_notice_count`/`test_notice_queued_count`,
`test_spill_count`, `test_logs`, `test_record`/`test_recorded`, `test_driver_reset`, `test_counters_reset`.
Stub-backed: `test_click`, `test_ui`, `test_menu`, `test_answer` (E6 inbox, then E2), `test_drain`, `test_phase`, `test_time` (E6).

`/datum/op_result` (key, outcome, reason, rolled, origin) is plain and never pooled. The engine fills it as the op ends; an op still waiting
returns it with a null outcome and the same pending op fills the same record later.

**Report calls each engine adds** (the recorder's store belongs to E6, which replaces `test_rec_event()`; the calls are fixed):

| Macro | Caller | Row (`kind`, `entity`, `key`, `from`, `to`) |
|---|---|---|
| `TEST_REC_OUTCOME(key, outcome, reason, actor)` | E2, when an op ends | outcome, actor, key, reason, outcome |
| `TEST_REC_LOG(key, outcome, origin, actor, target, text)` | E2, with the log line | log, actor, key, outcome, text (also queued for `test_logs()`) |
| `TEST_REC_RESOURCE(event, resource, holder, amount, op_key)` | E2, reserve/commit/release | the event, holder, resource, op key, amount |
| `TEST_REC_TRANSFER(item, from, to, slot)` | E2/E1, slot moves | transfer, item, slot, from, to |
| `TEST_REC_ACTIVATION(event, definition, source, holder)` | E1, attach/detach | the event, holder, definition, source |
| `TEST_REC_NOTICE(type, outcome, queued)` | E4, delivery or queueing | notice or notice_queued, type, outcome |
| `TEST_REC_DELTA(entity, key, from, to)` | E3, a tracked var or stat of a named entity changes | delta rows, kept only for entities named in `test_record()` |
| `TEST_REC_SPILL(key_chain)` | E3, a marked pass stops at its budget | spill |

`TEST_ROLL(percent)` is what `chance()` draws; `TEST_LANE_BUDGET(lane)` is what the drain reads; each stat evaluation charges `TEST_EVAL_COST`.

## Choices where the design was ambiguous or not expressible in DM

- Declaration lines cannot be compiled (`CAPABILITIES(...)` references `op()`, `hand()`...). They are no-op markers that swallow their arguments.
- `ACT_TRY` is a macro with a table lookup in the design; E0 has `e0_act_try(holder, act_type, ...)` taking the act type path.
- `grant(E, mirror_plating(reflect_chance = 45))` is not DM before E1: fixtures build a spec datum with `e0_mirror_plating(45)`.
- `test_answer(actor, value | REQ_*)` cannot tell the value 2 from `REQ_CANCELLED`; an outcome is the named argument `outcome =`.
- `test_ui(actor, window, ...)`: the window is identified by the entity hosting it, passed as `window`.
- The test species is `/datum/e0_species` with a learned `species` relation, so no real species machinery is built.
- Hit and notice-chain steps use fixture helpers over the stubs, because `chance()`, ACT_TRY and the hooks do not exist.
- ids are hand-assigned integers until the generators exist.

Not in E0 (named in section 19 but outside the task given): the compiled-table schema and entry struct, the `_generated` file formats, and the E5 query interface. They belong with E1 and E5, whose stubs above name the entry points.

**E5 (landed).** The query interface is the semantic layer of the analysis engine, `tools/analyze/src/sem/` (README section "Semantic layer"): `analyze gen` writes `code/engine/_generated/` (`reads.dm`, `system_accessors.dm`), and the other engines add their generators as `tools/analyze/src/gens/<name>.rs` on the `Generator` API. The lints `sem/keys`, `sem/reads` and `sem/handlers` resolve the ids and keys inside declaration markers, check generated reads, handler signatures, context fields, context escape, ACT_TRY pairing and purity. `READS_AS` and `READS_FROM` are markers (`code/__defines/engine/markers.dm`). E4: `ACT_TRY` has to survive macro expansion as a call (`ACT_TRY`, `act_try`, `e0_act_try`) for the pairing check; add another expansion name to `[lint."sem/handlers".lists] try_calls` in `tools/ci/lint_scopes.toml`.

**E1 (landed).** The declaration engine is `code/engine/declare/` (entries, capability definitions, the table builder, scoped activation, relations and the `rel_*` verbs with `LIST_STATE`, value schemas, state graphs, explain tools). The markers `CAPABILITIES`, `CAPABILITY_TYPE/DEF`, `cap_keys`, `STAGE_DEF`, `SOURCE_DEF`, `STATE_GRAPH` stay no-ops in DM; `analyze gen declare_ids` writes the ids they declare (`code/engine/_generated/ids.dm`, included early) and `analyze gen declare` the constructors, registration rows, state-key accessors and each type's `declared_entries()` (`declare.dm`); README, "Semantic layer". The contracts no longer carry numeric stat, source or stage ids (the generator assigns them; the capability ids the contracts give by hand are kept). Where the final syntax has no DM spelling, E1 chose: `link(A::a, B::b)` is rewritten by the generator (`link` is a BYOND keyword); `configure(CAP_X, "sel", p = v)` is rewritten to `configure(<constructor>("sel", p = v))`; the schema'd tracked var is `TRACKED_SCHEMA(T, v, schema)` (the legacy two-argument `TRACKED` stays), with `schema_text()` and `schema_path()` for the schema kinds BYOND owns (`text`, `path`); `not`, `all_of` and `any_of` as condition combinators are `cond_not`, `cond_all`, `cond_any` until E2's requirement language lands. The legacy `grant`, `revoke`, `granted`, `cap_of`, `without` and `stage` keep working: the final name dispatches on its first argument and falls back to `legacy_*`.
### E6 database and path transport (increment 5)

- `open_request(owner, /datum/io/sql/<kind>, handler, field = value...)`: a kind sets `query` (`:field` binds the request's var of that name, once, in order; `bound_fields()`), `row_type` and `expects_rows`. Rows come back as `row_type` datums; no match is `REQ_NO_RESULT`; no connection or a refused query is `REQ_TRANSPORT_FAILED` with `last_error`. `sql_write(query, params)` replaces `om_sql_write` for fire-and-forget writes. `db_query_now()` is the only blocking call.
- `open_request(owner, /datum/io/path, handler, start = turf, goal = turf)`: SSpathing runs one search at a time on a detached worker; no path is `REQ_NO_RESULT`; a goal on another z-level is `REQ_TRANSPORT_FAILED`.
- Not done in E6: the legacy `NewQuery()`/`Execute()` callers (still baselined sync_sql sites) and `dq_pathfind()` stay on their old paths.


**E3 (landed).** The stat layer is `code/engine/stats/` (defs, rules, contributes, store, recompute, status, vars_write), its constants `code/__defines/engine/stats.dm`, and `analyze gen stats` (`code/engine/_generated/stats.dm`, from the `STAT(T, name, RULE, ...)` markers; ids from `declare_ids`).

- A stat's effective value is a plain var, written only by the engine (`virtual = TRUE` declares no var: read it with `stat_value(E, STAT_X)`; the base stats of `/atom`, `/obj/machinery` and `light_range` are virtual, `/mob/living` ones are vars). A stat is composed from the type's own var default (a type-level contribution at default priority), the type's `contributes()` entries whose `when()` gates hold, and the holds, by the rule in `rules.dm`.
- Holds: `hold`, `hold_until`, `hold_override`, `release`, `release_all`, `held_by`, `held_by_source`, `hold_left`. The source is a live datum or a `SRC_*` id; null or text is a build report. A timed hold outlives its deleted source unless `bound`; an untimed one dies with it. `vars_write(E, name, value, source = SRC_VV)` on a stat is `hold_override` at `PRIORITY_ADMIN`.
- Statuses (`units =`) have a companion `STAT_<NAME>_IMMUNE` ANY stat (`immune_to`). The verbs are `stat_status_at_least/set/adjust/end/remaining` and `stat_has_status` (over holds on `HOLD_CLOCK_BIO`); the final names `status_*` stay with the legacy `/datum/proc` family until its ~700 callers migrate in phase 3 (an unqualified call inside a datum proc would resolve to the legacy proc).
- Settle rule, as built: a stat var read is current on the next line. A write recomputes the entity's own stats and the stats that read them (rank order) inline, `contributes_to` targets inline, one-relation hop readers inline when the edge is single-valued; collection edges, `SYSTEM_ACCESSOR` reads and multi-hop reads are marked (`GLOB.stat_marked`) and `stat_drain_marked()` recomputes them in rank order at the start of phases D, P and R under the lane budget shared by one kernel pass (`stat_tick_begin()`); what does not fit spills to the next drain (`TEST_REC_SPILL`). Initial evaluation at init is silent.
- Hooks into master code: `changed()` (var inputs), `own_field_changed()` (relation inputs), `rx_teardown()`, `engine_holder_init()`, the kernel's D/P/R phases and `test_slot()`, `condition_id_holds()` (a stat id is a condition).
- Not in E3: the legacy contribution store (`code/datums/om/contribution.dm`) stays authoritative for its `EFFECT_*` ids until phase 3; `BF_*` body-factor ids and the `/mob/living` status stats are phase 3 content; `grant()` of a SET stat's token is `hold(E, STAT_X, token, source)`.
- E5 integration: `contributes(STAT_X, PROC_REF(x))` reads come from `generated_reads_table`; a FORMULA stat's reads are written by hand (`reads = list(...)`) because a formula is not a hook handler. `analyze` now also treats the relation entries of `CAPABILITIES` blocks (`ref_one`, `owns_many`, `link`) as declared relations, and the system accessors and stat vars of test fixtures are generated inside `#if defined(UNIT_TESTS)`.
- `apc_flip_50` (`code/modules/benchmarks/apc_flip.dm`): one APC channel over 50 machines, per flip: old path (real machines running the body of `power_change()`) 0.82 ms, inline recompute 0.84 ms, marked plus drain 1.20 ms.

**E4 (landed).** The action and hook engine is `code/engine/actions/` (`act.dm`, `hooks.dm`, `notices.dm`, `change.dm`, `twins.dm`), its forms `code/__defines/engine/actions.dm`, and `analyze gen actions` (`code/engine/_generated/actions.dm`, from the `ACTION()` lines of `code/contracts/acts/world_actions.dm`) and `analyze gen event_twins` (`event_twins.dm`, from `tools/dx/codemods/om_event_map.json`).

- `ACTION(name, typed fields..., FIXED, notice =)` generates the act type, `act_<name>(holder, fields...)` (what `ACT_TRY(E, name, fields...)` expands to) and the past-tense notice with the same fields; a `hit/projectile` style name inherits its parent's fields (`act_hit_projectile`); a FIXED action has no act and `PUBLISH(E, name, field = v)` is `publish_<name>()`. A field called `origin` is `origin_turf`. The `op` action keeps the op context as its act and gets only `/datum/notice/op_done` (E2 sets `op_key`, which `on_op` filters on).
- `act_<name>()`: ACT_PASS when `act_wanted()` finds nothing (no hook of the action on the holder's table or activations, and no listener for its notice for any outcome, legacy `on_notice` and the OM event twin included); else `act_begin()` (depth cap), then `act_resolve()`: needs (the requirement language is E2's: `act_needs_refusal()` is the seam), the first `instead` in order (`when()`, `chance()` and `then()` parts; other parts reach `act_run_part()`, E2's), then every `adjusts()` (`field` is text, scale before by). `act_done(A)` ends ACT_COMMITTED and `act_cancel(A)` ACT_REFUSED, each delivering the notice only to listeners that asked for the outcome (`on_notice(..., outcome =)`, values combine with `|`; an outcome nobody asked for builds nothing), then releasing the act. `ACT_FINAL(F, field, local)` is the act's field, or the caller's local on ACT_PASS.
- A `/datum/notice` is a `/datum/act/notice` (parent_type) and pooled; it is also the context its handlers get (A.holder the entity whose entry runs, A.target the publisher, A.source the activation's source, A.outcome, the typed fields). A notice delivered by the engine also reaches the legacy `on_notice()` reactions of its holder, and a legacy `publish()` reaches the hooks, so both sides hear one occurrence.
- Depth: `GLOB.act_depth` counts running handlers. A nested notice published at depth 8 is queued (`GLOB.notice_late_queue`), delivered at the next drain point (`act_drain_point()`, called from `stat_drain_point()`, the start of the kernel's D, P and R phases) and reported through `act_report()` (a runtime that fails a test build; a test captures it in `GLOB.act_report_capture`); a nested action at depth 8 is not taken, ends ACT_REFUSED ("too deeply nested", `TEST_REC_OUTCOME`) and reports the same way.
- Hook forms: `extend(/datum/act/x, instead(...) | adjusts(field, by =, scale =, when =) | needs(...))` (parts are `/datum/entry`s, declared in `CAPABILITIES` and copied by the generator, which writes `adjusts(packet.amount, ...)` as `adjusts("packet.amount", ...)`), `on_notice(/datum/notice/x, parts..., outcome =)`, `on_op(key, parts..., outcome =)` (an `on_notice` of `op_done` with `op =`), `on_change(cond, ENTER | EXIT | ANY, parts...)`, `hook_capability(entries...)`, `observe(source, /datum/notice/x, listener, parts...)` and `unobserve()`, and `while_slotted(SLOT, entries..., on =)`, which now takes any entries (those that are not capabilities are wrapped in one `hook_capability`). The final names dispatch on their arguments and fall back to `legacy_on_notice`, `legacy_on_change`, `legacy_observe` and `legacy_unobserve`. `then(PROC_REF(x))` names a proc of the holder, `then(CAP_PROC(x))` a proc of the capability datum; `then()` and `chance()` are shared with E2's op parts.
- Hooks of an activation are `/datum/hook` records on `rx.hooks` (applied by the entry engines of the kinds `extend`, `on_notice` and `on_change`, removed by the one teardown path); a type's own are compiled once per table (`hook_table_of`, `act_plan_static`). Stacking decides which activations run (a shadowed activation's hooks are skipped); a static hook of a capability that has activations on the holder is represented by them. `on_change` is evaluated at the drain; a type-level one watches through `rx_readers()` (`hooks_watching()`), an activation's through `rx_watch_adjust()`; a read through a relation hop watches the relation var itself (E3's hop reverse index serves stats).
- `PUBLISH(E, name, ...)` and `WANTS(E, TYPE, outcome)` are the final macros; the legacy forms are `PUBLISH_LEGACY(E, /datum/notice/x, args)` (positional `take_notice()`) and the rx tables. `/datum/guard_ctx` is now a `/datum/act/action`. `/datum/op_ctx` is E2's to replace with the op context.
- The twins (`twins.dm`): `GLOB.event_twin_notice` maps an after-fact OM event to its notice and the notice's fields (renamed with a trailing `_` when the generated notice could not use the event's field name, which now includes the act context's own `holder`, `target`, `outcome`, `cap`, `activation` and `op_key`). `OM_EMIT` of such an event also publishes the notice, and delivering the notice also emits the event, each only when the other side has a listener (`om_wants()` asks `event_twin_wanted()`; `notice_wanted()` asks `notice_twin_wanted()`), and the bridge does not bounce. The map's last row deletes this file's rows (step A7).
- Counters for tests and metrics: `GLOB.act_taken`, `notice_taken`, `notice_late`, `act_too_deep`.
- Not in E4: the hit entry points (`bullet_act`, `receive_damage()` ...) still run the legacy damage path (A6 converts them to `ACT_TRY(src, hit_projectile, packet)`); the `Moved()`, `Crossed()` and `Bump()` adapters; `needs()` requirements and the other Do parts (E2); the ledger's slot moves do not call `activations_slot_enter()` yet (E2's `slot()` and `put_in()`).

**E2 (landed).** The part engine is `code/engine/parts/` (`part.dm` the part constructors, `cond.dm` conditions and requirements, `plan.dm` the op compiler, `provider.dm` providers and the actor and reach gates, `resolve.dm` candidates and ordering, `inputs.dm` the click, menu, UI and topic inputs, `run.dm` the four stages and the pending op, `resource.dm` reservations and adapters, `explain.dm` the explain tools, `prompts.dm` the few prompt kinds the engine itself asks), its constants `code/__defines/engine/parts.dm`, and `analyze gen ui_types` (README, "Semantic layer").

- An op is `op(key, parts...)`; every part is an interned `/datum/entry/part` subtype whose stage hooks are procs on its type. The compiler folds an op and what is addressed to it (tool profile, own parts, group extends, key extends) into one `/datum/op_plan`, cached on the type's table (`T.op_index`; a granted capability's ops in `T.op_def_indexes`). Table build reports a plan problem (an effect above `asks()`, a `captures()` with no workflow step, a requirement with no reason, two ops with the same input, intent and tier) through `table_error()` with the op's file:line.
- Resolution (`op_resolve`): candidates from the target, the held item (`at_target`, `in_hand`) and the actor; pass 1 runs the cheap gates (actor gate on `acts_via`, origin, authority, the binding's input, intent, providers and reach), pass 2 the `when` conditions. Order: intent rank, tier, target before held before actor, declaration order, then `priority(above/below)`. The menu (`action_options`) and the screentip share it; a menu read is memoised per entity set and invalidated by an epoch (`op_changed()`: `changed()`, capability key publication, provider set changes).
- The engine (`op_begin`): Require (implicit `req_capable`, bay, `needs`, costs availability, the pre-checks of effects), Wait (a `/datum/pending_op` that holds holder, target, actor and held through declared relations with `OTHER_DELETE_ME`, so deleting one cancels the op with feedback; keeps re-checked every `WAIT_RECHECK_INTERVAL`), Do (reserve, `chance()`, effects reporting `OP_*`, commit or release, feedback, log, `op_done`). `perform_op`, `action_options` and `screentip_for` dispatch on their argument shape and fall back to `legacy_perform_op`, `legacy_action_options` and `legacy_screentip_for`; `req`, `all_of` and `any_of` likewise (`legacy_req`, `legacy_all_of`, `legacy_any_of`). The legacy `req_empty_hand`, `req_self_held`, `req_access`, `req_stance` and `req_heard` datums gained `holds(A)` so `needs()` takes them.

## Phase 2 additions

**The hit bridge.** `receive_damage(packet)` (`code/game/atom/damage_packet.dm`) now starts the engine's hit action before the legacy reactions. `hit_act_type(packet)` maps the packet to the most specific hit action: `DAMAGE_ENTRY_PROJECTILE` to `hit/projectile`, `EMP` to `hit/emp`, `EXPLOSION` to `hit/explosion`, `BLOB` to `hit/blob`, `WEAPON` and `GENERIC` to `hit/melee`, `SHOCK` to `hit/shock`, an entry-less packet with `armor_flag == FIRE` to `hit/fire`; thrown hits and direct deliveries are the generic `/datum/act/hit`. A hook declared on `/datum/act/hit` applies to every subtype (`hook_applies` is a path test), so there is one `ACT_TRY` per hit, never a second one for the parent. `hit_try()` first asks `act_wanted()`: a holder with no hook and no listener pays that one check and allocates nothing (`GLOB.act_taken` stays put), and behaves exactly as before.

Semantics when something is hooked: `needs` refuses the hit (outcome `ACT_REFUSED`), the first `instead` that runs takes it over (`ACT_REPLACED`); both mean nothing lands and `receive_damage()` returns 0 (the packet gets `DAMAGE_PACKET_BLOCKED`). `adjusts(packet.amounts, scale =, by =)` now accepts a list field: scale then by apply to every positive entry, never below zero (`packet.penetration` and other numbers work as before). When the hit proceeds, the legacy `DAMAGE_REACTION` rows run next (a block there ends the act `ACT_REFUSED`), then the sink, then the after rows, then `act_done()` delivers `/datum/notice/hit/<entry>` to its listeners, after the sink. A refusal or take-over is logged (`HIT: ...`). Also fixed: `needs(req...)` inside `extend()` was the op language's part and never became a hook; it is now a `HOOK_NEEDS`. No content type uses the bridge yet.

**`ruined()` in `dismantle()`.** `dismantle(tool(...), becomes(frame), ruined(cond, becomes(scrap)))`. The condition is any section 9 condition, evaluated with `op_cond()` and the dismantle op's context (a `PROC_REF` or `TYPE_PROC_REF` of `x(datum/act/A)`). The dismantle op now runs: its input parts, then the ledger refund, then the dismantle's effects (or, when a `ruined()` holds, that entry's effects in their place; several `ruined()` entries are tried in order, none holding runs the ordinary effects), then the instance ends unless a `becomes()` already replaced it. Only effect parts (and `then()`) belong in `ruined()`; others are reported. Refund choice: the whole ledger is refunded whether or not the dismantle is ruined (section 12: "It refunds the whole ledger"; ruined swaps what the thing becomes, not what the crew put in). The refund now runs before the effects, because `becomes()` deletes the instance and its history with it.

**Wipers (the rag).** `wiper(soaks_from =, burning =, wipe_time =)` (`code/library/reagents/wiper.dm`) beside `reagent_container(needle = TRUE, ...)`: `soak` (a click on a tank or bucket of the listed types: it takes as much as it holds), `wring_into` (an open container: five deciseconds a unit, with a begins() message) and `wipe` (anything else that is not a person: three seconds, then `atom/on_rag_wipe()`; a dry cloth refuses). `burning` names the holder var that says it is alight (nothing is wiped, wrung or soaked then). **Synthesizers (the cyborg hypospray and drink synthesizer).** `synthesizer(containers =)` (`code/library/reagents/synthesizer.dm`) is only the two ops a click answers: `inject` (a living thing) and, with `containers`, `dispense` (an open container); what they do (the store, the recipe, the checks, the messages) is the holder type's own, `extend("synthesizer.inject", then(PROC_REF(injected)))`. **Doses (pills, patches).** `dose(route =, dose_wait =, pierces =, cuts_into =)` (`code/library/reagents/dose.dm`) is a thing taken whole and used up, beside `reagent_container(needle = TRUE, sealed = TRUE, settable = FALSE)`. `route = CHEM_INGEST` gives `take` (a click on yourself: all of it into the stomach) and `force` (on another, after `dose_wait`; a mask, no mouth or a belly refuse); `route = CHEM_TOUCH` gives `apply` and `stick` (the limb aimed at: a missing or robotic limb refuses, and thick material unless `pierces` names a true holder var; the thick-hide roll of some species is made when it goes on, `can_inject(..., roll = FALSE)` leaves it out of the requirement). `dissolve` is a click on an open container with something in it (all that fits goes in), and `cuts_into` (a type) adds `cut`: a sharp thing or an ID card cuts it into one of that type. **Needles (syringes, droppers).** `needle(modes =, needle_time =, draws_from =, fills =)` (`code/library/reagents/needle.dm`) sits beside `reagent_container(needle = TRUE, sealed = TRUE)`: `sealed` is a container that is never open (`atom/is_open_container()` is false whatever the lid), which is what a syringe is. `modes` names the holder var of the mode (`NEEDLE_DRAW`, `NEEDLE_INJECT`, `NEEDLE_BROKEN`, `NEEDLE_CAPPED`); with none (a dropper) the container draws while it is empty and puts out while it holds something. The transfers are the ops' effects (a `then` runs before a resource commit, so what is told must be what moved). `begins(msg | PROC_REF(x), others =)` (`code/engine/parts/part.dm`) is told when an op starts its first wait, where `says()` is told at the commit. `req_reagent_room(of =)` is a requirement that the holder of the subject has free space. `reagent_container(injects = TRUE)` is the instant injection of a hypospray (op `inject`, one RES_REAGENTS transaction into the blood).

**Reagent containers (glass, bottles, buckets, paint cans).** `reagent_container()` (`code/library/reagents/`) is what `/obj/item/reagent_containers/glass` and its beaker, bucket, kettle, bottle and paint lines run on. A setting of it that is a fact of the type (`volume`, `transfer_default`, `transfer_min`, `transfer_max`, `starts`) is a number or list written in the declaration, or the name of a var of the holder (`volume = nameof(volume)`): the type keeps it on its own var line and a subtype or a map edit changes it there. More params: `starts_open` (a lidded container whose lid is off at the start), `taps` (types that are drawn from while their top is shut, by their own amount: the `fill` op), `rests_on` (a key of `GLOB.reagent_containers_can_be_placed_into`: a click on one is never a pour or a splash, so the target's own interactions get it), `feed`/`feed_wait` (a click on somebody else), `examine_range`, `settable`, `spray_cooldown`, `shows_contents`, and `spray` (the container sprays instead of pouring: `REAGENT_FLOW_SPRAY`, `atom/reagent_spray_at()` is what a type overrides for another shape of spray; spray bottles are in `code/modules/reagents/reagent_containers/spray.dm`). Which op a click is, is decided by `when()` conditions (a pourable open holder, a tap, a splashable thing), never by a refusal: a refusal ends the click, so only a click no op answers falls through to the legacy handlers. `pour`, `fill` and `splash` sit at the part tier or above, so they come before a legacy `INTERACTION_HANDLED_PASS` entry of their target (a pass-through entry would otherwise end the click). The lid op is used in hand or picked from the menu (an empty hand on a container picks it up); `set_amount` is the menu and an alt-click. `REAGENT_FLOW_INGEST` is a drink or a feeding: the units are swallowed (`trans_to_mob(..., CHEM_INGEST)`: the ingested holder, with the taste); `drink` is a click on yourself in a stance that is not hostile (half for a small mob), `feed` the same on another after `feed_wait`. `reagent_transfer_amount(thing)` is how much one transfer from it moves (a capability's chosen amount, else `atom/legacy_transfer_amount()`, which `/obj/item/reagent_containers` and tanks answer from their var); `req_reagents(units, more =)` is a requirement (and so a condition) on the holder's volume. `atom/is_open_container()` follows the capability's lid key; the old `cap_reagent_container` library, its test and the `CAP_LID_OPEN` bit are gone. A glass container's own handling (label with a pen, dip a small thing, test blood with a hot one, milk venom, the bucket's sensor, steel frame, mop and wirecutters, the paint can's paint) are the `glass_handling` and `glass_container` bundles and the types' own entries in `code/modules/reagents/reagent_containers/glass.dm`.

**Storage items (`/obj/item/storage`: bags, boxes, belts, backpacks, pill bottles, toolboxes, lockboxes).** `storage()` (`code/library/containers/storage.dm`) is what every storage item runs on. The contents stay in the containment ledger's storage slot (`CONTAINER_SLOT_STORAGE`, the ledger relation `/datum/om/relation/slot/storage` in the same file: `slot()` entries are not read by the ledger yet, so the slot is still a decl type), but what it takes is the capability's: `refusal()` is the one rule set, and the slot's `refusal()` and capacity ask it, so `move_into()`, `slot_transfer()`, the code API (`insert_item()`, `remove_from_storage()`) and the ops all apply it. A type declares what it takes in its own list with `configure(storage(accepts = list(types), refuses = list(types), max_size = ITEMSIZE_X))` (the hundred and forty-five `TYPE_TABLE(..., hold_spec, HOLD_ONLY/HOLD_NOT/HOLD_MAX_SIZE)` rows of storage types became those; `HOLD_*` still serve holsters and grippers); `space`, `slots` and the switches are names of vars of the holder, as `reagent_container()` does it. One instance narrows itself with `storage_restrict(holder, types, max_size)` (the activation's `/datum/cap_data/storage`; `restrict_hold()` of an exact-fit kit). Ops, all `storage.<name>`: `put_in` (`when` the held item would go in), `refuse` (the same click when it would not: it says why, lowest tier, `passes()`), `gather` (a held pickup bag on a storage; `passes()`, so the bag may then go into it, as before), `open` (an empty hand on a carried one; a pocketed one comes to the hand), `toggle_open` (alt-click), `empty_out` (use in hand), `empty` and `gather_mode` (menu). Window opening, the HUD and the code API stay procs of `/obj/item/storage`. Conditions about the contents read `held_count()`, `held_things()` or `holds_good_bulb()` (a `READS_AS` accessor of `STORAGE_CONTENTS_KEY`, published when a move changes the slot) or the library requirement `req_storage_empty()`. Other library parts: `quickdraw(starts =)` (state key `QUICKDRAW_DRAWS`), `two_hands()`, `req_not_worn(slot)`; `lock(alt = FALSE)` leaves the alt-click to the holder (a lockbox opens on one).

Two engine fixes the conversion needed, tests in `dq_p2_storage_engine/*`: **`passes()` is honoured in a click** (`op_passes_chain()` in `code/engine/parts/inputs.dm`: an op that ends committed and passes lets the next candidate whose conditions hold run, and so on; when the chain ends on a pass a player's click goes on to the mob's own click handling, the way a legacy entry's `INTERACTION_HANDLED_PASS` did; a refused op passes nothing). **A read of a holder's contents is not a write** (`dq_ledger()` lifts the purity guard and the self-mark check while it builds a ledger or adopts contents that arrived without a move, `GLOB.ledger_adopting`): the first condition or look to ask about a storage whose things were made inside it with `new` used to trip the guard.

What storage does not do yet: the HUD datum (`/datum/storage_hud`) keeps its `own_*` writers, vore eggs still hatch through `om_task_timed`, wallets keep their EMP `DAMAGE_REACTION`, and pouch removal keeps its named task. Tests: `dq_p2_storage/*` (behaviour, written and green on the old code first, only their adapters changed), `dq_p2_storage_engine/*`.

**Tables (`/obj/structure/table`, benches, racks).** A table is one `CAPABILITIES` list (`code/modules/tables/tables.dm`): the build ladder `table_frame()` (a graph: frame, plated by any `stack(/obj/item/stack/material, 1)`, reinforced by a second one dragged on, and `dismantle()` of a bare frame into steel), the carpet, repair, flip and put-in-place ops of its own, and `on_op` hooks that redraw when a layer goes on or off. The plating and the reinforcement are the graph's: `material()` and `reinforced()` read `built_material()` of the plated and reinforced stages, and a preset table is built by `set_layers()` (it walks the graph with a synthetic ledger of one sheet per layer, so a layer comes off and gives its sheet back the same way). Two engine changes: a click's parameters are readable by the effects it runs (`op_resolve_click_with_params()`), and a player's drag of an item onto a holder with ops resolves as `GESTURE_DRAG` before the old `MouseDrop_T` (`/datum/input_adapter/proc/drag`). Climbing is the library's `climb(landing = ...)`: the flipped-table landing is the table's own proc, and a flip shakes climbers off with `climb_shake_off()`. What tables keep in their legacy form: the look (`DECLARE_APPEARANCE_PROC`), the projectile cover check and the break into parts; they wait for the look parts.


**Doors (steps 1 to 3).** `then(handler, early = TRUE)` runs an effect before the op's other effects (an electrified door's shock). `op_resolve_click(.., defer_legacy)`: when

that are not converted yet. `claims()` (an op holds its target while it waits; a second claiming op is refused with `/datum/msg/op/claimed`; `op_claimed(target)`
reads it, the claim lives on the target's `rx_state`) and `req_unclaimed()`. `computed(PROC_REF(x))` as an `asks()` field. `graph_advance` does nothing for a holder
that a stage's effect already replaced. `multitool_settings(list(list(label, var, "text"|"frequency", max, hint)))` (library). Emag: every `emag()` also brings the
cardless `subvert` op, which `emag_target()` uses for holders without a legacy declaration. Keyed relations: `analyze gen` writes `declared_keyed_targets()`
(`ref_one/ref_many(by =)` of every `CAPABILITIES` list), read at start by `link_entries_for()`, so a table built before any holder's table (a door placed before its
button) is keyed. A prompt kind `/datum/prompt/choice` now lives in `code/library/prompts/`.

**Engine gaps found by the phase 2 conversions (`dq_eg2/*`, `dq_eg2_wait/*`).**

- *Prompts reach a player.* `/datum/prompt` has a transport: `begin()` shows the kind's window to an answerer with a client (`code/engine/present/prompt_windows.dm`: tgui alert, list, text, number, colour, checkbox and bitfield windows, and a radial ring), and a window answers through `prompt_window_answer()` into `request_submit()`, which runs the kind's `normalize()` and `refusal()` (a refused answer leaves the question open and shows it again); closing or timing out ends it `REQ_CANCELLED` / `REQ_TIMED_OUT`. `request_answer()` (the driver) goes through the same check. Kinds: engine `yes_no`, `text` (`max_len`, `name_text`), `number` (`min_value`, `max_value`, `step`); library (`code/library/prompts/kinds.dm`) `choice` (`choices`, `buttons`, `radial`, `anchor`, `radius`), `color`, `checklist`, `bitfield`. A kind's `prepare(datum/act/A)` fills it from the asking op; a field written `computed(PROC_REF(x))` is `x(datum/act/op/A)`'s value when the op asks. `typepath` and `colormatrix` are not built (no converted op asks them yet). Proofs: the bible's chaplain use (a radial `choice`), the polychromic wallet (`color`).
- *Waits show and break.* `wait()` draws a progress bar on the actor and a cog on onlookers (silent_wait() opts out; an `ORIGIN_SYSTEM` wait draws nothing) and the new `STAY` keep, in `WAIT_KEEPS_DEFAULT` for a non-system actor, cancels it when the actor walks; an open question outlives a step (`STAY` is dropped for `asks()`). `on_interrupt(PROC_REF(x))` runs `x(datum/act/op/A)` (with `A.reason`) when the wait or question is broken, never on completion. A delay the code API needs while an actor waits (`stall_insertion`) is an op with `ai()` and `wait()`, started by `perform_op(user, src, key, held, ORIGIN_AI, AUTH_AI | AUTH_PHYSICAL)`: the slow pouch.
- *Held verbs.* `held_verb(verb_path, slots = SLOT_ANY_HELD)` (`code/library/items/held_verb.dm`) grants the item a verb through the verb store while a mob carries it in those slots (`SLOT_ANY_CARRIED` is a hand or anything worn, a pocket included); it replaces `DECLARE_VERB` on `set src in usr` verbs. The verb starts an op.
- *Drags carry mobs.* A drag is a typed `/datum/input_event/drag` (`inbox_drag()`, `test_drag()`); the target's ops see the dragged atom as `A.held` (`item(/mob/living)` binds a mob), and what no op answers goes on to `drag_legacy()` (the gesture entries, then `MouseDrop_T`). A dragged mob is no provider. An op with `by(0)` needs nothing of its provider and reaches what is adjacent to the actor (a mouse has no hands). The storage `climb_in` op replaces the one `INTERACT_DRAG` entry.
- *Natural weapons on a click.* `clicks()` binds an actor's own op to its click on a target (candidate on the actor's side only, physical, `ORIGIN_CLICK`); `natural_weapon` is `inputs(ai(), clicks())`. A click is routed through the resolver for a mob whose index has such an op (`op_has_click_ops()`, one flag read).

## Several pending ops per actor (rewrite/multi-pending)

`GLOB.op_pending_by_actor` maps an actor to the list of its pending ops (oldest first); `op_pendings_of(actor)` returns the live ones, `op_pending_of(actor)` the oldest, `op_pending_for(actor, key)` the one of an op key. The contract:

- An actor's pending ops are not exclusive. A question (`asks()`, `confirms()`) holds nothing and never keeps another input out.
- Exclusivity is `claims(mask)` (`CLAIM_HANDS | CLAIM_BODY | CLAIM_TARGET`, `code/__defines/engine/vocabulary.dm`). `op_claim_hold(plan, binding)` is what an op holds while pending: its declared mask, else hands and body for a timed `wait()` on a physical binding, else nothing. `op_claim_check()` is what a starting op needs free: what it holds of the actor, plus the hands for any physical input. The actor's side (hands, body) is held only while a timed wait step runs (`pending_op.timed_wait`); the target side lasts the whole pending op (`rx.claimed_by`, `op_claimed()`).
- `op_begin` order: duplicate (same op key and target with an open question: `focus_prompt()`, the existing op's result comes back, nothing starts), then conflicts (a player's input cancels each overlapping pending op with `/datum/msg/op/stopped`, an AI's is refused with `/datum/msg/op/busy`), then Match, Require, the target claim (`/datum/msg/op/claimed`) and the cap (`OP_PENDING_CAP`, `/datum/msg/op/too_many_pending`). ORIGIN_SYSTEM ops are in no actor's list and neither wait on nor end it, as before.
- Every pending op keeps its own subscription (`watch_begin`), its own request and its own window; ending one leaves the others alone. Every cancellation goes through `cancel(reason)` and tells the actor.
- `request_answer(actor, value, outcome, op_key)` and the driver's `test_answer(actor, value, outcome, op_key)` answer the actor's oldest open request, or the one of the op named. `/datum/prompt/focus()` brings an open window to the front (`prompt.focused` counts it).
- Pinned by `dq_prompt_interrupt/*` (no existing test encoded the single slot), including the multi-pending tests in `dq_multi_pending_tests.dm`.
