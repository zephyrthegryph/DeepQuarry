The model

Six ideas cover the whole API. Everything else in this document is a constructor for one of them, or a library built from them.

Entries

What a type declares, in one inheriting list per type: CAPABILITIES(T, ...). Capabilities, ops, stats, relations, triggers, outputs, look parts. Built once per type and interned.

Parts

The unit of behaviour inside a trigger: how it's reached, what it requires, what it costs, what it does, what it says. Interned values that nest into bundles.

Stats

A value composed from contributions by one rule. Its effective value lives in a plain var that only the engine writes. Built on the existing OM contribution store.

Sources

Whoever holds a runtime contribution: a capability, an item, a spell, an admin, a timer. One source holds once. Releasing, expiring or deleting it takes back everything it held.

Triggers

Things that run parts. Ops (chosen by an actor), actions (refusable world events), notices (it happened), changes, timers and periodic work. Every trigger has a typed context.

Systems

World-level owners of global state and periodic work, scheduled by the kernel with boot order, budgets and membership. They replace subsystems, world services, world lanes and the OM scheduler.

input→gesture→bind profile + stance→action (ACT_*)→candidates: target, held item, actor→offered→priority→route + provider→check→pay (wait cancels early)→commit→feedback→notice
setter / stat / hold / relation write→publish key (only if read)→hooks: on_change+conditions re-evaluate: stats, every(when), requirements, steps+outputs queue: look, UI, Rust, HUD, derived→presentation phase, once per frame

Ground rules

  1. One form per job. Each need has exactly one form, listed in this document. A second form is a defect: the lint for the old one is shrink-only, and reaches zero by the end of the migration.
  2. Declarations are pure and per type. Entries never read instance state. A capability's setting can name a var or a proc, which is resolved per instance at runtime.
  3. State changes only through setters, stats, holds and relation accessors. These are the only things that publish. Raw writes to tracked state are build errors.
  4. Reads are generated, never typed. The build derives what every condition and output reads. The only hand-written key is the one named by an on_change hook.
  5. Every effect runs inside a trigger. Effects never sleep. Waiting is a wait() part, a timer or await(). There is no spawn, gameplay sleep, INVOKE_ASYNC or do_after.
  6. Refusals are requirements. A requirement returns null to allow, or a reason. It never has side effects, so menus, examine and early cancels can ask it at any time.
  7. Global state lives in systems. There are no new globals, subsystems, world services or fire().
  8. Memory scales with distinct declarations, not with types or instances. Everything declarative is interned, and a type that adds nothing shares its parent's compiled tables.

1Declarations

#define CAPABILITIES(T, entries...) // expands to T/declare(list/into) { ..(); into += list(entries) }
  • Inheritance is automatic: the parent's entries always come first, and there's no . = ..() to forget.
  • Repeats compose: several CAPABILITIES lines on one type chain in file order. A one-line data-only subtype is just CAPABILITIES(T, configure(...)).
  • Build time: the table builder walks the list once per type, interns every entry, and splits it into the runtime indexes: op resolver, trigger index, relation table, stat table, look parts and verb table.
  • Sharing: a type whose list adds nothing shares its parent's compiled tables.

Precedence

The same order applies everywhere: library defaults (tool profiles, a capability's own parts), then the declaring type's parts, then extend(tag), then extend(key). At each level a subtype beats its parent. Requirements always accumulate, so no level can drop one another level added. Single values (a wait, a priority, a message) take the most specific declaration. without(key) applies at its position in the list.

Interning and memory

  • Flyweights. Parts, requirements, ops and capabilities are interned by signature, so tool(TOOL_MULTITOOL) is one datum everywhere. That's already true today for capabilities and /datum/req.
  • Per-instance cost: stat vars; one bitfield per boolean stat for contribution results; the hold list, allocated only while something is held; per-instance capability data, allocated on first use; and relation vars.
  • Procs stay off base types. Library behaviour lives on capability datums or global procs taking the holder, never on /atom: each /atom proc costs about 0.5 MB, and B2 measured 13 MB saved for 27 procs.

Replaces: capabilities(), reactions(), relations(), ownership(), derived(), declared_capabilities(), CAPABILITY(), DECLARE_INTERACTIONS and EXTEND_INTERACTIONS, every lifecycle DECLARE_*, REGISTRY_MEMBERSHIP, DECLARE_VERB*, DECLARE_APPEARANCE*, DECLARE_UI* and MAP_RESOLVER (as an entry).

2Kernel and systems

The tick

One kernel replaces the Master Controller loop, SSbehaviours (the OM scheduler), world lanes and the subsystem fire() model. Each server tick runs fixed phases under one budget:

PhaseRuns
K hostSystems that wrap BYOND or the process: input, verb queue, garbage, database, tgui transport
N nativeOne vg_frame(elapsed, budget); its outbox becomes publishes, notices and band crossings
U urgentReserved slice for request_urgent() and on_cross(..., urgent = TRUE)
D deadlinesDue timers (after()), hold expiries, op waits ending
P phased workevery() work items and sequences (Life), ordered by after edges, paid from lane budgets
R presentationQueued outputs once per entity: looks, UI pushes, HUD, derived values, Rust pushes
G garbageDeferred deletion work

  • Latency classes L0–L3 decide what's shed first under load. Input and urgent work never shed.
  • Metrics: every work item, step and system reports its cost through metrics() into the kernel profiler, which replaces the OM profiler.

4Tracked state

TRACKED(T, var) // generates T/proc/set_<var>(value): compare, write, publish the key "var" if anything reads it SETTER(T, var) // registers a hand-written set_<var>() that has side effects; it calls tracked_changed(src, nameof(var))
  • Settings and plain state are plain vars made TRACKED. The lint rejects any write outside the setter, and admin var edits go through the setter.
  • Base vars anchored, density and opacity are tracked, through their existing hand-written setters (B4).
  • Settings vs effective state. A var is a setting (what someone chose) or effective state (what is currently true), never both. Effective state that more than one thing can force is a stat (section 5). The turret's enabled is a setting; its armed is a stat.
  • Capability state (cover open, panel open, locked, bolted, emagged, lid open) is tracked. Each bit publishes its own key ("cover_open"), and a bit that several things can force is a stat. The duplicated machine fields go away, so each fact exists once: emagged, locked, and broken.
  • Derived values: derive(nameof(v)) plus derive_<v>() is a one-formula value owned by the type: a stat with one contribution. Its reads are generated.
  • Keys that aren't one var (MOB_KEY_EQUIPMENT, OCCUPANTS_KEY) are published by their producer with PUBLISH_CHANGE(E, key). An accessor proc that stands for such a key declares it with READS_AS(proc, KEY), so generated reads resolve it (section 7).

Replaces: OM_FIELD, OM_FLAG_FIELD, OM_DERIVE_FIELD, OM_FIELD_SETTER, 3-argument TRACKED, TRACKED_BRIDGED (after the machine and Life tracks), om_changed and changed(E, CHANNEL), the CHANGE_* channels, cap_set's catch-all publish, machinery fields duplicated as capability bits, stat_add/stat_remove for owned bits, and manual *_changed() notify calls.

5Stats, holds, grants and overrides

A stat is a value composed from contributions by one rule, stored in a plain var only the engine writes, and published when its effective value changes. The engine is the existing OM contribution store (contribution.dm). It already has rows of (stat, source, value, expiry, key), timed and held entries, release on source deletion, combine rules, re-apply stacking and composites. This section is its final API.

Holds: runtime contributions

hold(E, nameof(stat), value, source, lasts = null, priority = 0, clock = CLOCK_OWN) release(E, nameof(stat), source) release_all(E, source) // everything one source holds on E held_by(E, nameof(stat)) // the sources (a fresh list) hold_left(E, nameof(stat), source) // deciseconds left on a timed hold
  • One source holds once. Holding again replaces the value and keeps the later expiry, so a second EMP extends; it never leaks (review D2).
  • Expiry is one deadline per entity, on the chosen clock. Deleting a datum source releases everything it holds, everywhere.
  • Admin edits of a stat var become a hold by the admin, visible in VV and removable. They're never a raw write the engine would overwrite.
  • Cost. A boolean stat keeps one bit per static contribution per instance, and re-evaluates only the contribution whose reads changed. The hold list exists only while something is held. Generated reads see the stat var like any other var.

Grants are holds on set stats

grant(E, what, source, lasts = null) // what: a capability type, a verb path, hidden_verb(path), an ability, a language, a trait, an access id revoke(E, what, source) granted(E, what)
  • Capabilities. Granting a capability attaches its entries to that one instance (ops, triggers, contributions, look parts). Revoke or expiry detaches all of them.
  • Verbs. Granted verbs and hidden verbs are members of the instance's verb set, and the verb store applies them. A hide beats a grant.
  • Traits. has_trait(E, X) is granted(E, X).

Conditional entries

when(condition, entries...) // an automatic grant whose source is the condition

The condition's reads are generated, so the framework attaches and detaches the entries itself. No code calls a "changed" proc. Species, preferences, worn items and modes all use this: when(PROC_REF(spont_vore_on), spontaneous_vore()), when(nameof(emagged), emagged_menu()).

The pipeline, every time

  1. Offered and check. These run when the menu is built, when the op is chosen, after every wait and right before commit. A wait cancels early when a requirement's read publishes. An actor has one wait at a time.

Damage

Entry points (bullet_act, hitby, ex_act, emp_act, fire_act, blob_act, melee, shocks) build a pooled packet and run the /datum/act/hit/<entry> action. The pipeline then runs in order:

  1. Requirements: immunities and godmode, as stats.
  2. Intercepts: shields, reflection, the APC's blob rip.
  3. Mitigation: armour stats, materials, resistances.
  4. The sink: damage_sink(), which is integrity for objects and injure() for mobs.
  5. The notice: /datum/notice/hit/<entry>.

  • Timed statuses are holds.

  • Periodic medical work (contagion spread, symptom ticks) is every() or a Life step.

Mob Life

  • The sequence: Life is /datum/sequence/life. Its steps are procs declared with seq_step(); subtypes override the proc, and traits and organs add steps through granted capabilities.
  • Outputs: HUD and vision are output() entries with generated reads, at_most and a when = nameof(client) gate. Nothing calls a refresh.
  • Stats: movement and acting are stats (can_move, can_act).
  • Observers: ghosts, AI eyes and blobs use every() on their own type.

Machines

  • Working: operable is a stat. powered(), breakable(), construction(), emp_disable() and admin holds contribute to it.
  • Power draw: power_draw is a TOP stat (off, idle or active, each contributed by whatever is running). The power system reads it.
  • Work: machine work is every(interval, ..., when = nameof(operable)), or a narrower condition.
  • Systems: machines join theirs through powered_by() or membership().
  • Parts: the parts() capability derives stats such as efficiency and capacity from the installed parts.

Simulation and Rust

  • The frame: the native system runs vg_frame in phase N.
    • Its outbox becomes CHANGED publishes, notices (/datum/notice/native/<event>) and band crossings for on_cross.
    • DM reads Rust-owned values as native("key") (cached per frame), and those reads are generated like any other.
  • Pushes: DM-owned settings Rust needs are tracked vars. push_to_rust() is an output that writes them with native_write(), and its reads are generated, so it runs once per frame after a setting changes.
  • Thresholds are watches: on_cross(native("pressure"), list(50, 100), parts..., urgent =).
  • Gas and heat: gas mixtures stay opaque handles (return_temperature(), set_temperature(), vg_pump, ...). The heat API stays: get_temperature(), add_heat(), set_temperature().
  • Bindings: the generated vg_* procs and the ABI handshake stay.
  • Scheduling: DM timers and keys live only in the kernel. The Rust world scheduler keeps native watches and rate models.

World systems

Every former world service and subsystem is a system:

  • Machines and mobs: machine, mob, plant.
  • Infrastructure: power, chemistry, radiation, sound, POIs, supply, research, chat, statpanels.
  • Rounds and events: votes, events, expedition, flight, sun, night shift, explosions, turf cascade.

Each has needs, every() work, membership, and an api.dm. On-demand systems park while idle.

Mob AI

ai(behaviours) is a capability. Its behaviours run on every() or a sequence and act through perform_op() and perform_action(): the same ops, requirements and messages a player uses. Aggro, targets and stances are stats and relations.

Eight phases. Each lands on master when it passes its gate, under the existing rules: one worktree per worker; compile, focused tests and one full suite; fast-forward to master; follow-ups fixed on master. 22Source layout

The new tree is organised by what a file is for, not by where it came from. Framework code, shared capabilities, large systems with their own model and ordinary content each get a top-level folder under code/. A file moves into the new tree only when it is fully migrated.

The tree

code/engine/{kernel,time,state,stats,refs,change,actions,parts,hooks,present,io,_generated}
    // the framework: one folder per section of this document.
    // _generated holds the build step's reads tables and is never hand-edited.
code/library/{machine,access,containers,reagents,items,structures,construction,providers,mobs}
    // shared capabilities and bundles (section 11)
code/domains/{body,damage,atmos,power,life,ai,verdigris}
    // big systems with a model of their own
code/content/<domain>/...
    // e.g. content/machinery/power/apc.dm, content/doors/airlock.dm
code/world/
    // systems, world services, map glue, round flow

    // split per engine and library module; replaces __defines/

Migration rule

A file lives in the new tree only when it is fully migrated. So the old directories (code/game, code/modules, code/datums and the rest) are the remaining-work list: when they are empty, the migration is done.

Each wave does the same four things in order:

  1. Convert the files in the wave.
  2. Prove them: zero old forms (per-file ratchet), tests, the construction round-trip and the bench.
  3. Move them in a pure git mv commit, with no edits, so history follows.
  4. Merge.

Old APIs are deleted in the commit their last caller goes. The lint for that form flips from a ratchet to a hard ban at that point, not all at once in phase 7.

The design is against origin/master 0d7f401f27. The inventories behind it are five read-only surveys (the OM layer, the sys layer, the current framework, subsystems and services, and the docs) plus a mechanical scan of every framework macro, proc and hook (api_surface.py). Section 17 is generated from that scan (mapping.py) and checked against the whole document (coverage.py). Code in sections 1–16 is design, not compiled.
